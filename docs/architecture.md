# Архитектура системы

Проект строится по **серверно-авторитарной модели (Authoritative Server)** по **Варианту Б**: мета-сервер и игровой узел вынесены в два отдельных Rust-бинарника, а игровая симуляция полностью изолирована в отдельном крейте.

## 1. Компоненты и их ответственность

```text
┌─────────────────────┐      HTTPS / REST       ┌──────────────────────┐
│  Веб-клиент (TS)    │ ──────────────────────► │  meta-server (Axum)  │
│  или Tauri Desktop  │                         │  + SQLite (sqlx)     │
└─────────┬───────────┘                         └──────────▲───────────┘
          │                                                │
          │ WSS (бинарный протокол)                        │ POST /internal/match-result
          ▼                                                │ (X-Internal-Secret)
┌─────────────────────┐                                    │
│  game-node (Axum)   │ ───────────────────────────────────┘
│  (без БД, 20 TPS)   │
└─────────┬───────────┘
          │ вызовы
          ▼
┌─────────────────────┐      Этап 3 (офлайн)    ┌──────────────────────┐
│  game-core (Rust)   │ ◄────────────────────── │  game-wasm (Worker)  │
└─────────────────────┘                         └──────────────────────┘
```

### `crates/game-core`
- Чистая детерминированная симуляция мира (`World`, `Player`, `Zone`, `Building`, `Unit`, `Projectile`) и кодек бинарного протокола.
- **Жёсткое ограничение:** никаких зависимостей от сети, файловой системы, БД, `std::time::Instant::now()` и `rand::thread_rng()`.
- Шаг времени `dt` (или номер тика) и сидированный генератор случайных чисел (`SmallRng`) передаются снаружи — это гарантирует компиляцию в `wasm32-unknown-unknown` и детерминизм.

### `crates/game-node`
- Быстрый WebSocket-узел на **Axum + Tokio**, обслуживающий игровую комнату на `20 TPS` (тик = `50 мс`).
- **Не зависит от `sqlx` / SQLite:** проверяет JWT игрока локально в памяти по общему `JWT_SECRET` (гости подключаются без JWT, только с ником).
- При гибели игрока асинхронно отправляет результат матча в `meta-server` (`POST /internal/match-result`). В LAN-режиме (Этап 3) эта отправка отключается.
- Готов к горизонтальному масштабированию по регионам и переиспользованию в локальной сети.

### `crates/meta-server`
- HTTP REST API на **Axum + Tokio** и база данных **SQLite (`sqlx`)**.
- Отвечает за регистрацию/вход по email, выдачу JWT, профили игроков, статистику, глобальный лидерборд и выдачу списка доступных `game-node` (`GET /api/servers`).
- В Этапе 3 сюда же добавляется авторизация Telegram Mini App и хранение скинов/достижений.

### `crates/game-wasm`
- В MVP — минимальный каркас/заглушка в workspace.
- В Этапе 3 компилирует `game-core` в WebAssembly и запускается внутри Web Worker в браузере для офлайн-режима с ботами.

### `client/` и `src-tauri/`
- **Веб-клиент:** чистый TypeScript + HTML/CSS + Vite + Canvas2D.
- **Слой `transport/`:** абстракция `Transport` (`send(bytes)`, `onMessage(handler)`). В Этапах 1–2 используется `WsTransport`, в Этапе 3 — `WorkerTransport` без изменения кода рендера, ввода и UI.
- **Отдельные настройки подключения:** `API_BASE_URL` (для `meta-server`) и `GAME_WS_URL` (для `game-node`). При локальной разработке Vite проксирует запросы, при деплое статику раздаёт Nginx/CDN, а в Tauri клиент упакован локально и ходит на удалённые серверы.
- **`src-tauri/` (Этап 2):** тонкая десктопная оболочка вокруг собранного `client/`.

### `config/balance.json`
- Единый источник истины для параметров арены, стоимости/HP/урона построек, юнитов, кривой XP и характеристик.
- Читается в `game-core` через `serde_json` (в `game-wasm` вшивается через `include_str!`) и отдаётся клиенту (при сборке Vite или через `GET /api/config`).

## 2. Жизненный цикл одного действия и тика

1. **Ввод на клиенте:** игрок кликает по карте для постройки турели. Модуль ввода переводит координаты экрана в относительные `(rel_x, rel_y)` от центра зоны и формирует бинарный пакет `0x02 Build`.
2. **Доставка в комнату:** `WsTransport` отправляет байты по WebSocket в `game-node`. WS-обработчик Axum декодирует команду и кладёт её в `tokio::sync::mpsc` канал игровой комнаты.
3. **Обработка тика (раз в 50 мс):**
   - Цикл комнаты вычитывает все накопленные команды из `mpsc` и передаёт в `world.apply_command(player_id, cmd)`.
   - `game-core` проверяет валидность (достаточно ли Энергии, внутри ли радиуса зоны, нет ли коллизии с другим зданием) — при ошибке формирует `0x86 ActionError` конкретному игроку.
   - Вызывается `world.step(0.05)`: добыча ресурсов, спавн юнитов, движение по пространственной сетке, стрельба турелей, урон, начисление XP.
4. **Рассылка снэпшота:** `game-core` сериализует текущее состояние в бинарный `0x82 Snapshot`, а `game-node` рассылает его всем подключённым сессиям.
5. **Рендер на клиенте:** цикл `requestAnimationFrame` (60+ FPS) интерполирует позиции между двумя последними снэпшотами и рисует кадр на Canvas2D.
